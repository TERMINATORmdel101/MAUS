# MAUS — Security design of the elevated engine (Microsoft Store review)

This document answers the ten points requested by Microsoft Store certification for the restricted capability `allowElevation` (policy 10.6.3). It describes MAUS **0.8.6**, the version submitted with this document (source: https://github.com/TERMINATORmdel101/MAUS). Every statement below was checked against the source code (last review: 2 November 2026, commit `a7e5cbf`; the additions of §2.6 and what refers to them: commit `e7c18a2`), and file paths are given so a reviewer can verify them. Where a protection does **not** exist, this document says so. Version 0.8.5 follows a complete review of the code against this document (30 October 2026): the engine was changed where the document promised more than the code did (battery report never served by the engine, forced undo ignored from the channel, every driver action confirmed by the engine, bounded free texts, bounded `schtasks` wait), and the document was corrected where the code is the intended behaviour. Version 0.8.6 tightens it further; each change is marked "since 0.8.6" below (allowlist of registry keys in the accessor, weekly audit without network, local folders only for `space`, stricter `process.terminate`, bounded preferences, winget never started with administrator rights, a benchmark started by the engine that writes nothing in the user profile).

The package also declares the restricted capability `unvirtualizedResources`, so that the writes described in §3 reach the real registry and file locations instead of a copy private to the package (`installer/msix/AppxManifest.xml`). It adds no operation and no target to §1 to §3.

MAUS is a free, open-source (GPL-3.0) Windows 11 maintenance utility. It has no telemetry and no network service. An audit started by the user uses the network in two read-only ways: the Windows Update module asks the Windows Update Agent for pending updates (M03), and the software module lists available upgrades with `winget upgrade` (M20), which since 0.8.6 runs only without administrator rights (§2.5). Since 0.8.6 the optional weekly scheduled audit makes no network access: M03 reads what Windows found in its own last search (`IUpdateSearcher.Online = false`) and the update history kept by Windows (§2.6), and M20 does not run winget (its finding is reported as not checked, and the weekly score is kept on a separate curve). Everything else that uses the network is started by the user: Windows repair (DISM can download from Windows Update), software upgrades and PawnIO through winget, links and web searches opened in the browser, the ping test. MAUS sends nothing about the PC to its author or to any service of its own; a web search that the user starts sends the searched name to the search engine the user chose. Some links that the user opens also carry a hardware model in the URL: tutorial searches on YouTube (CPU, GPU or PC model) and BIOS searches on the vendor's site (PC or motherboard model). Nothing is sent unless the user opens the link.

## 0. Architecture

`MAUS.exe` (the user interface) runs **without administrator rights** (manifest `asInvoker`), and nothing is elevated at start.

MAUS opens in **limited mode**: every control that needs administrator rights is greyed out, and the read-only audit stays available without rights (§7, §10). When the user explicitly clicks **"All features"**, the interface starts a second copy of the **same executable**, `MAUS.exe --engine <pipe-name> <ui-pid> <key-fingerprint>`. It uses `ShellExecute` with the verb `runas`, so Windows shows its UAC prompt.

The elevated copy (the "engine") behaves as follows:
- It first validates its own command line. The pipe name must match `^MAUS-[0-9a-f]{32}$`, the PID must be a positive decimal number and the key fingerprint must be 64 lowercase hexadecimal digits; otherwise it exits with code 2 without doing anything (`src/Maus.App/App.xaml.cs`, `RunEngineAsync`). The same applies when `--engine` does not come with exactly these three values: it never opens a window instead.
- It accepts a **closed list of operations** over a named pipe, only from the process named on its command line, and only requests signed with that process's secret key, each with a sequence number that can be used once (§5). A client that disappears while connecting only makes the engine reopen the pipe, with the same checks (0.8.6).
- It stops when the interface exits, or after 15 minutes without any request, or (since 0.8.6) about 60 seconds after its start (the engine checks every 15 seconds, so the stop comes between 60 and 75 seconds) if the interface never presented its key. It also stops at the user's request ("Close rights", §7).

The interface never sends a command line, a script, a registry path, a registry value to write or an executable path. It sends an operation name, identifiers and options from closed sets, plus three bounded free texts that are never executed and never written to Windows settings: the restore-point description (passed to Windows as the name of the point), the verification notes stored in the MAUS journal, and the protected preferences object (§4). It can also send one folder path, for the disk-space analysis only (`space`, §4): the interface only sends the roots of fixed drives, the engine accepts only a local path with a drive letter, whatever its spelling (§4), and the folder is only enumerated, read-only. The engine recomputes everything it does from its own audit, its own lists and its built-in catalogs.

Code:
- `src/Maus.App/EngineHost.cs`: launch.
- `src/Maus.Core/Engine/Broker/`: `OnDemandMausEngine`, `EngineServer`, `RemoteMausEngine`, `EngineProtocol`, `LocalMausEngine`.

## 1. Exact allowlist of engine operations

The engine dispatcher (`EngineServer.cs`, `EngineServer.Workshop.cs`) recognises exactly the 31 operation names below. Any other name returns the error "Opération inconnue" (unknown operation), and nothing is executed.

**Needs administrator rights** column. "Yes" means the operation needs administrator rights. In limited mode (engine not running), every control that leads to such an operation is **greyed out**, and the controls made to start the engine are the "All features" button of the banner at the top of the window, the startup window, the "Enable advanced sensors" button and, only when the weekly task still points to the folder of an earlier Store version or keeps the rights given by an earlier version, the "Put back in place" button of the notice on the home page. That last button is not greyed out in limited mode: after MAUS's own Yes/No question it calls `schedule.set`, so UAC appears for that one action and declining cancels only that action (§7 also states one narrow exception, after a user action); the operation itself then runs in the engine. "No" means the operation also works without rights: it goes through the engine only if the engine is already running (it then runs with administrator rights), otherwise it runs in the non-elevated interface. A "No" operation never starts the engine and never shows UAC (`OnDemandMausEngine.cs`, methods `Elevated` and `Available`).

The list of winget upgrades (`software` up to 0.8.5) is not an engine operation since 0.8.6 either: the interface reads it itself, without administrator rights, even when the engine runs, and the dispatcher no longer recognises the name (§2.5).

## 2. Commands, APIs, executables, arguments and targets

No operation accepts a command line, an executable path or a script from the interface, and no value from the interface is placed on a program's command line as free text; the free texts and the `space` folder of §0 are the only free-form inputs. Executables are fixed in code and resolved from protected folders; winget then runs the publishers' installers (§6). An automated test (`tests/Maus.Core.Tests/Security/SecurityGuardTests.cs`) makes the CI run fail in the cases below. The `Tests` workflow runs the whole test suite, with warnings treated as errors, on every push and pull request. The script that builds the Store package (`installer/msix/build-msix.ps1`, also run by the `Paquet du Store` workflow) builds with warnings as errors and runs the same tests first: if the build or one test fails, no package is made.
- a program is started from any source file other than the 8 reviewed launchers;
- `UseShellExecute = true` is used anywhere other than the `runas` launch of the engine;
- `cmd.exe` is started anywhere other than `VisibleConsole`, or `VisibleConsole` is called from anywhere other than `SoftwareConsole` (interface, without administrator rights).

### 2.1 `apply` and `revert` (fixes)

Fixes are written only by `FixEngine` (`src/Maus.Core/Fixes/FixEngine.cs`) through `SettingsAccessor.Write` (`src/Maus.Core/Fixes/SettingsAccessor.cs`). The one other caller of that accessor is `RestorePointCreator`, for the restore-point frequency value (§2.3). There are exactly five kinds of write (`SettingKind`):

| Kind | API | Target |
|---|---|---|
| `Registry` | `RegistryKey.CreateSubKey`, `SetValue`, `DeleteValue`; on undo or rollback, `DeleteSubKey` (Win32 registry API through .NET) | Only the values of the plan that the engine computes from its own audit and catalogs: those listed in §3.1. Since 0.8.6 the accessor itself enforces an **allowlist** of those keys (`src/Maus.Core/Fixes/SettingAllowlist.cs`: key prefixes, and the permitted value names for keys that hold other values, such as `Services\<name>` → `Start` only, `Winlogon` → `Shell` and `Userinit` only, `Image File Execution Options\<exe>` → `Debugger` only, matched on that exact key); any other key is refused before the write, on apply and on undo alike. The plan remains the first barrier, and the channel carries no registry path or value |
| `SystemParameter` | `SystemParametersInfoW` with `SPIF_UPDATEINIFILE \| SPIF_SENDCHANGE` | 10 visual-effect flags of the current user (§3.1, M06) |
| `MinimizeAnimation` | `SystemParametersInfoW(SPI_SETANIMATION)` | Minimize/maximize animation of the current user |
| `ActivePowerScheme` | `PowerSetActiveScheme` (powrprof.dll, documented API) | Active power plan: only the built-in Windows plans "High performance" or "Balanced" (fixed GUIDs), chosen by the engine from the audit (the accessor accepts any parsable GUID, but the GUID comes from the engine's plan, never from the channel); undo restores the previous plan's GUID read before the change |
| `ScheduledTask` | `%SystemRoot%\System32\schtasks.exe /Change /TN <path\name> /DISABLE` (undo: `/ENABLE`), arguments passed separately (`ArgumentList`), through `SchtasksTool`, the code also used by `schedule.set` and `schedule.get` (since 0.8.6 it stops `schtasks` with its process tree after 30 seconds for a fix, and after one minute for `schedule.set` and `schedule.get`) | Third-party logon tasks found by the M12 audit. Tasks under `\Microsoft\` and disabled tasks are never listed, and since 0.8.6 the accessor itself refuses a task under `\Microsoft\` |

Besides these writes, `apply` can make the calls of §2.3 for a restore point (WMI `SystemRestore.CreateRestorePoint`, with the frequency value set to 0 around the call) when the option is on, and WMI `SystemRestore.Enable` on the Windows system drive (normally `C:\`) when protection is off and the user allowed it. `apply`, `revert` and `verify` also write the journal files of §3.2. `revert` creates no restore point.

After an apply or undo that changed something, the engine broadcasts `WM_SETTINGCHANGE` (`SendMessageTimeoutW`, `SMTO_ABORTIFHUNG`, 2 s) so that Windows picks up the change.

### 2.2 `tool`: three fixed tasks, run directly and shown by MAUS

Since 0.8.6 the engine starts no command interpreter and leaves no elevated prompt behind. `SystemTool.RunAsync` (`src/Maus.Core/Platform/SystemTool.cs`) starts the tool from `%SystemRoot%\System32`, with each argument passed separately (`ArgumentList`), no shell and no window; the working directory is System32. What the tool writes goes back over the signed channel as progress messages, and the interface shows it read-only with a progress bar (`ToolWindow`). The window accepts no input. When the task ends, the engine returns a result text based on the exit codes.

| Task (`ToolKind`) | Exact command | Input accepted and validation |
|---|---|---|
| `Repair` | `DISM.exe /Online /Cleanup-Image /RestoreHealth`, then `sfc.exe /scannow` | None |
| `DriverAction` | `pnputil.exe` with one of: `/restart-device <InstanceId>` · `/remove-device <InstanceId>` then `/scan-devices` · `/export-driver oem<N>.inf <backup folder>` · the same export, then `/delete-driver oem<N>.inf /uninstall` **only if the export succeeded** | Action from a closed enum (Restart, Reinstall, Backup, Remove). The device must be a **display adapter** in the driver list the engine reads itself, at the moment of the request. An action outside that enum is refused before the driver list is read and before any question; the checks below also run before the question. Its instance id must be under 400 characters and match `\A[A-Za-z0-9_\\&.\-#{}]+\z`. Reinstall only for `PCI\` devices. Backup and Remove only for third-party packages `oem<number>.inf` (never a Windows inbox driver). The backup folder is built by MAUS and created by the engine: `%ProgramData%\MAUS\pilotes\<yyyyMMdd-HHmmss>-<inf name>` |
| `DriverRestore` | `pnputil.exe /add-driver <backup folder>\*.inf /subdirs /install` | Backup folder **name** only: 1–200 characters, no invalid file-name characters, no `\` or `/`, not `.` or `..`. It must not end with a dot or a space. It is resolved inside `%ProgramData%\MAUS\pilotes`, must exist and must contain an `.inf` file. The path must be under 250 characters and contain none of `" % ! & \| < > ^`, CR or LF. Since 0.8.6, before any file in it is looked for, the folder, each subfolder and each file must be owned by SYSTEM or Administrators, give no other account a right to write, delete or change permissions, and not be a link (a file must have a single name); otherwise the restore is refused with a message (`WindowsDirectoryProtector.IsTrustedTree`) |

For restart, the delete step of Remove, and restore, the exit code of `pnputil` gives the result (0 = success, 3010 = restart needed, 259 = nothing to update, for restore only, anything else = failure; `GraphicsDriverActions.Outcome`). Backup and Remove stop if the export fails. Reinstall runs both steps and interprets no exit code. Repair runs SFC even if DISM fails and reports the exit code of DISM.

If the interface closes during a task, the interface asks first; the engine then stops waiting and exits. MAUS does not kill the running tool, because cutting a repair or a driver operation would be worse, but the next step of the task is not started, and the tool may stop by itself once it can no longer write its output.

**winget is never started by the engine** (since 0.8.6, neither to install nor to list upgrades, §2.5). Software upgrades and installing or removing PawnIO are started by the interface, without administrator rights (`SoftwareConsole`), in a visible console: `%SystemRoot%\System32\cmd.exe /d /s /k "…"` (`VisibleConsole.Run`; `/d`: the `AutoRun` value of the registry is not run), working directory System32. An installer that needs administrator rights asks for them itself, through its own UAC prompt, and never inherits those of MAUS. If MAUS was started with "Run as administrator", `SoftwareConsole` refuses and asks the user to reopen it normally. `SecurityGuardTests` checks that `SoftwareConsole` is the only caller of `VisibleConsole.Run`.

That command line contains only fixed text, the winget path, package ids and display text:
- `winget.exe` is used **only** from the `Microsoft.DesktopAppInstaller_8wekyb3d8bbwe` package folder under `%ProgramFiles%\WindowsApps`, by exact package family since 0.8.6. The alias in the user profile is never used (`Winget.Locate`, `ReadOnlyCommandRunner.IsInProtectedAppsFolder`). A winget path that contains `"` is refused.
- Upgrades: for each chosen package, `"<WindowsApps>\winget.exe" upgrade --id <ID> --exact --source winget`, the upgrade commands are added while the line stays within 7,500 characters; the number of packages left out is shown at the end. Each id must contain only ASCII letters, digits and `. - _ +` (`SoftwareUpdate.CanTarget`). MAUS itself is left out, because its installer refuses to run while MAUS is open. Winget stays interactive: the user accepts the publishers' licence terms in the console.
- PawnIO: `"<WindowsApps>\winget.exe" install --id namazso.PawnIO --exact --source winget`, or `uninstall` (id fixed in code).
- Displayed text, including package names, is escaped (`RepairConsole.Escape`): `^ & | < > ( )` are escaped, `%` and `!` are removed, `"` becomes `'`, line breaks become spaces.

It then deletes the folder and returns the exit code, the result and the image to the interface, well within the 32 MiB message limit (§4). The interface, without administrator rights, adds the result to its history and writes the image in the user profile (§3.2). With administrator rights and no `--output`, the benchmark keeps nothing and does not open the history or the images folder, and it refuses `--result`, `--screenshots` and `--capture`. A window started as administrator receives the result the same way and does not write it in the profile; it tells the user. Without a running engine, the benchmark runs without administrator rights and keeps its result in the user profile itself, as before |
| `prefs.save` | Atomic file write | `%ProgramData%\MAUS\settings\preferences.json`; when the existing file is damaged or was written by a newer version, a copy `preferences.json.illisible-<date>` is kept beside it first |

**Tests that add no engine operation (since 0.8.6).** The screen, keyboard and mouse, speaker, battery, Wi-Fi walk, cooling, combined-load and USB capacity tests run in the interface, without administrator rights. The keyboard and mouse test reads input only inside its own window while it is in the foreground (WPF events; Raw Input for the mouse only, without `RIDEV_INPUTSINK`) and stores nothing. The USB capacity test asks for a confirmation, writes only new temporary files on a removable drive chosen by the user, and removes them; existing files are not touched.

### 2.4 Read-only commands used by the audit

The audit runs external tools only through `ReadOnlyCommandRunner` (`src/Maus.Core/Platform/ReadOnlyCommandRunner.cs`):
- the executable **and** its arguments are checked against an allowlist;
- a tool named without a folder is taken from `%SystemRoot%\System32` **only**: if it is not there, it is reported as missing, and the `PATH` is never searched;
- winget is accepted only from WindowsApps, and since 0.8.6 only in a process without administrator rights: an elevated process (the engine, a window started as administrator) refuses it before starting it (§2.5);
- anything else is refused before starting.

Allowed commands:
- `powercfg /list`
- `bcdedit /enum {current}`
- `fsutil behavior query DisableDeleteNotify`
- `reagentc /info`
- `nvidia-smi` with the three fixed queries of `GpuDriverModule`
- `winget upgrade --source winget --disable-interactivity` (without administrator rights only, since 0.8.6)
- `dism /English /Online /Cleanup-Image /CheckHealth`
- `powercfg /batteryreport /output <fixed MAUS path>`
- `powercfg /batteryreport /output <fixed MAUS path> /xml` (since 0.8.6)

Since 0.8.6 each line must match entirely, argument by argument, ignoring case; `netsh`, `dsregcmd` and `manage-bde` are gone (the WinHTTP proxy is read with `WinHttpGetDefaultProxyConfiguration`).

The two `powercfg /batteryreport` lines each accept their own single path and nothing else (`/duration`, `/transformxml` and any other argument are refused). Each writes that one report; no audit module uses them, only the interface (§2.3). The XML file is deleted once read.

The audit also reads the registry, WMI/CIM, event logs, the package list and files through read-only interfaces (§2.5, §10).

**Where the reserved space comes from.** `%ProgramData%` above is never taken from the environment. A single place (`src/Maus.Core/Platform/SystemPaths.cs`) computes it: the drive comes from `GetSystemWindowsDirectory`, and the location from the raw value of `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\ProfileList\ProgramData`, with only the Windows drive and the Windows folder substituted and no other variable expanded; any other form of that value gives `<Windows drive>\ProgramData`. Every use goes through it.

**Checks before the reserved space is used** (`WindowsDirectoryProtector`, before every read and every write):
- the folder must be under that root, or it is refused and left untouched;
- each folder above `MAUS`, up to the drive root, must not be a link, must be owned by SYSTEM, Administrators or TrustedInstaller, and must give no other account the right to delete, move or change the permissions of what it holds. The default rights of Windows pass this check: they let any account create a folder there, which is why `MAUS` itself is reserved;
- `MAUS` and the folder itself are then reserved as described above.

If this fails, the engine reads nothing from that folder. `journal` and `session` return the reason, `revert` restores nothing and says why, and `prefs.load` returns the default choices with the reason as a notice, so no "wanted" mark is taken from it. A process without administrator rights can neither protect nor read this space, so it reads nothing from it, as if it were absent. Files written by earlier versions in the protected folder keep the rights they inherited from it, and stay readable.

**Environment of an elevated process.** The environment of an elevated process comes partly from the profile of the account. The engine, a window started as administrator, the elevated benchmark and the separate command-line tool therefore set `SystemDrive`, `SystemRoot`, `windir`, `ProgramData`, `ALLUSERSPROFILE`, `TEMP` and `TMP` back to their machine values when they start (`SystemPaths.ResetEnvironment`), for themselves and for what they run. `TEMP` and `TMP` become the machine value of `HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Environment`. When elevated, the published `MAUS.exe` launcher sets the same variables before .NET starts (`src/Maus.App/Host/MausHost.cpp`), from `GetSystemWindowsDirectory` alone (`<Windows drive>\ProgramData`, `<Windows folder>\Temp`); MAUS then replaces them with the values above. A process without administrator rights keeps its environment.

### 3.3 Services, tasks, drivers and other configuration

- **Tools (§2.2):** MAUS fixes the command, but the tool sets the scope. `DISM /RestoreHealth` repairs the Windows component store and `sfc /scannow` replaces damaged protected system files. `winget upgrade` and the PawnIO install or removal start third-party installers without administrator rights from MAUS; an installer that obtains them through its own UAC prompt can change files, services, tasks and drivers, chosen by that installer, not by MAUS. `pnputil` changes the driver store for the selected display adapter. The statements below about services, tasks and drivers, and the "Never touched" list, describe MAUS's own actions, not what these tools and installers do.
- **Services:** MAUS itself starts, stops, creates or deletes no service. Only the `Start` value of the 10 services listed in §3.1 can be restored to the Windows default, and only when that service is disabled.
- **Scheduled tasks:** `\MAUS\WeeklyAudit` can be created, deleted or re-pointed (§2.3). Third-party logon tasks can be disabled and re-enabled (§2.1). Tasks under `\Microsoft\` are never changed.
- **Drivers:** apart from PawnIO below, MAUS's own driver actions concern only the display adapter, only through `pnputil` (§2.2). Every action is confirmed in the interface and, since 0.8.5, confirmed a second time by the engine itself (restart, remove and re-detect, back up, back up then delete, restore; §8). Before a driver is deleted, the interface requests a verified restore point first (`restorepoint.driver`; if it fails, the user decides whether to continue; the driver is backed up first in any case). Since 0.8.6 the interface shows the restart to everyone and the other actions (remove and re-detect, back up, back up then delete, list and restore backups) only in technician mode (Settings); this is a display choice, the engine operations and their checks are the same. MAUS ships no kernel driver.
- **PawnIO:** PawnIO, a signed third-party driver, is installed or removed only through winget, at the user's request, in a visible console; its installer adds its kernel driver. When PawnIO is installed and MAUS has administrator rights, MAUS uses it to read data, and MAUS's own code calls no fan or other control API (`src/Maus.Core/Workshop/Memory/PawnIo/SpdBusDriver.cs`, `PawnIoMemorySources.cs`). What it reads:
  - sensors, through LibreHardwareMonitorLib (processor and motherboard only);
  - memory SPD chips;
  - memory-controller registers (Intel `IntelMCHBAR` / `IntelMSR` modules, AMD SMN register reads);
  - the AMD power-management table (an SMU command that refreshes the table, then a read).

  A software guard in front of the SMBus module examines every transfer call (`ioctl_smbus_xfer`) and refuses writes, except the page-selection writes that reading an SPD chip requires (addresses 0x36/0x37 for DDR4; register MR11 at addresses 0x50–0x57 for DDR5). Since 0.8.6 a DDR5 page write must carry a page number from 0 to 7 and goes through only after the chip at that address has identified itself as a DDR5 SPD hub (registers MR0 and MR1 read 0x51 and 0x18), so it cannot reach the contents of a DDR4 chip; and the guard refuses every module function other than the transfer and the three that the SPD library calls for detection (identification, port selection, write-protection query). MAUS therefore cannot modify an SPD chip or a DDR5 power-management IC through the transfer function. When the BIOS enables its SPD write protection on DDR5, MAUS does not work around it: it reads only the first page of the chip and says so (since 0.8.6). On AMD, refreshing the power-management table is a mailbox command sent to the SMU (a hardware write that only asks for the table to be updated), followed by reads. The software guard covers the SMBus module only. It does not cover LibreHardwareMonitorLib 0.9.6, whose metadata names hardware-write functions (`DisableIOSpaceLock`, `WriteIoPort`), which the library may use to reach motherboard sensors. MAUS does not call them itself, and it has not been traced which boards reach them, so "to read data" is established for MAUS's own calls and is not proven for that library's internals.
- **System protection:** WMI `SystemRestore.Enable` on the Windows system drive (normally `C:\`) is called only during `apply`, only if system protection is off **and** the user allowed it (`ApplyOptions.EnableProtectionIfNeeded`): by the option, or since 0.8.6 by answering Yes to "Enable system protection and continue?", asked when protection is off and not when a policy turned it off.
- **Temporary ETW sessions:** `NT Kernel Logger` (latency, at most 5 minutes) and `MAUS_Compteur` / `MAUS_Releve` (PresentMon), stopped at the end and when the engine stops normally; if the engine process is killed or crashes, see §9, item 11.
- **Display:** the refresh-rate trial (`ChangeDisplaySettingsExW`) runs in the **non-elevated** interface, never in the engine. The trial mode is applied dynamically (not saved) and rolled back automatically after 15 seconds unless the user clicks "Keep"; "Keep" then saves the mode through the same API (`CDS_UPDATEREGISTRY`). This is the one setting that the interface itself changes outside the FixEngine journal (§9, item 12, lists the other changes outside the journal); since 0.8.6 the interface keeps a note of it in the user's settings, and the History page offers to go back to the previous rate (same API, same non-elevated process, and it leaves the display alone if its rate has changed since). That rate comes from the user's settings file, so it is written only after the user's Yes, only if Windows lists it for that display at that resolution, and only after a `CDS_TEST` of the mode accepts it. If the interface dies during the 15-second trial, nothing was saved: the dynamic mode stays until the next display change or restart, then the saved mode returns.
- **Never touched:** BIOS/UEFI, BCD and boot configuration, Defender exclusions, firewall rules, hosts file, proxy, page file, user accounts, credentials, CPU mitigations (MAUS only re-enables them).

## 4. Inputs, permitted values and validation per operation

General rules (`EngineServer.cs`, `EngineProtocol.cs`):
- A message is a 4-byte little-endian length, a 1-byte type, then either the 32-byte key (presentation: at most once per connection, and only the key whose fingerprint was given at start is accepted) or a 32-byte signature followed by the UTF-8 JSON body (since 0.8.6). A length ≤ 0 or above **32 MiB** is refused before the body is read.
- Every request is signed (HMAC-SHA256) and carries a sequence number that can be used only once (§5). A request with a wrong signature closes the connection without an answer, and no JSON at all is parsed before the signature is checked (since 0.8.6); a request with a used number is refused the same way, after parsing and before anything is executed.
- One request per connection. A malformed message closes that connection; nothing is executed.
- JSON is deserialized into fixed record types. Unknown fields are ignored. A missing or wrongly typed field returns an error, and nothing is executed.
- Identifiers (`Checked`) must have 1–200 characters, with no control characters and no `\`, `/` or `:`. At most **500** identifiers in the `apply` list. This check applies to `apply`, `module`, the session id of `verify`, `revert`, `session` and the `frames` session name; the `tool` fields have their own rules (§2.2). The free texts are bounded too (0.8.5): the restore-point description (1–200 characters, no control characters) and the verification notes (at most 500 entries of at most 2,000 characters); the list of acknowledged findings in `prefs.save` is bounded since 0.8.6 (at most 500 entries; finding id of 1–200 characters without control characters; stored value of at most 2,000 characters; language tag `fr`, `en` or `es`), and the Game Bar profile must be 1, 2 or 3. Marks are kept and compared in a bounded form: a longer value becomes its beginning followed by its SHA-256 digest, so a change in the part that is cut still ends the mark. A longer value written by an earlier version (0.8.5 had no bound) is put in this form when the file is read, so the bound of `prefs.save` is unchanged and such a mark does not get every later save refused. The list of kept refresh rates holds at most 500 entries, with a source name and a label of at most 200 characters. The list of unticked audit modules is bounded in number and length as identifiers are, without control characters; a newly unticked module is confirmed by the engine itself.
- Enumerations travel by name only: since 0.8.6 a number in place of a name is refused when the message is read (`EngineProtocol.Json`). The operations that act on an enumeration also check that the value is defined (`schedule.set` since 0.8.5, `prefs.save` and the driver action of `tool` since 0.8.6; `tool` already refused an unknown kind).
- An optional identifier (`changeId` of `revert`) may be absent or null, which means the whole session; any other type is an error.
- Language: if it is not one of fr, en, es, the engine uses the language of Windows. It only selects message texts.

## 5. Named-pipe authentication, authorization, process verification and anti-replay

| Control | Implementation |
|---|---|
| Engine command line | The pipe name must match `^MAUS-[0-9a-f]{32}$`, the client PID must be a positive number, and the key fingerprint must be 64 lowercase hexadecimal digits; otherwise the engine exits (code 2) |
| Unpredictable name | `MAUS-<random GUID>` (`Guid.NewGuid`, 122 random bits), generated by the interface for each engine start |
| Pipe squatting | The first instance is created with `PipeOptions.FirstPipeInstance`: if another process already owns the name, the engine fails to start instead of serving it. Later instances do not use that flag, and the ACL grants `CreateNewInstance` to the user's account, so another process of the same account could create an instance of the same name once the engine runs: the interface then refuses that instance (the server process id does not match, see below) and sends nothing; at worst the engine stops after 3 refused connections. Denial of service, with the interruption effects of §9, item 7 |
| Access control list | Explicit `PipeSecurity`: **Deny** `NETWORK` (S-1-5-2) full control, and **Allow** the account the engine runs under (`ReadWrite \| CreateNewInstance`). Since 0.8.6, when the UAC prompt was approved with another account (a standard account and an administrator's password), a third entry **allows** the person signed in to the session (`SessionUser.Sid`), `ReadWrite` only, because the interface runs under that account; its process and key are verified like any other connection. Remote clients are refused |
| Client verification (engine side) | For **every** connection, `GetNamedPipeClientProcessId` must equal the client PID (passed on the engine's command line; only its format is validated). In normal use, this is the interface that started the engine. Any other process is disconnected without an answer, and the attempt is recorded in the engine's in-memory breadcrumbs (§9, item 10) |
| Server verification (interface side) | For every connection, `GetNamedPipeServerProcessId` must equal the PID of the engine process that the interface started itself (`Process.Start` result). Otherwise the interface refuses to use the pipe and tells the user. Since 0.8.6 the first answer is also checked: if the signed `ping` does not report that same PID and administrator rights, the interface does not use that engine and stays in limited mode |
| What is not verified | The engine trusts the PID and key fingerprint on its own command line. It does not check its parent process, or the executable path, signature or integrity level of the client, and the interface does not check those of the engine beyond the PID. A program running in the user's session could therefore start `MAUS.exe --engine` itself with its own PID and fingerprint. UAC would still appear, showing MAUS, and if the user approves, that program is the engine's client: it can send only the closed list of §1 with the validation of §4, and the engine's own confirmations of §8 still appear. This was traced in the code, not run |
| Secret key | For each engine start, the interface draws a new 256-bit key from the Windows cryptographic random generator (`RandomNumberGenerator`). The key is **never** put on the command line, which other programs can read: only its SHA-256 fingerprint is. On its first connection, the interface presents the key over the pipe; the engine accepts it only if its SHA-256 matches the fingerprint it received at launch (constant-time comparison), and keeps it for its lifetime. Before that, every request is refused (`src/Maus.Core/Engine/Broker/EngineKey.cs`) |
| Request authentication | Every request is the exact UTF-8 bytes of the JSON `{operation, language, arguments, sequence number}`, sent in a binary frame after an HMAC-SHA256 signature computed with the key (domain-separated: `MAUS-REQ`). The engine checks the signature (constant time) **before** parsing any JSON: since 0.8.6 the frame itself contains no JSON outside the signed body. A missing, short or wrong signature closes the connection without an answer and counts as a refused connection |
| Anti-replay | Each request carries a sequence number that the interface increments. The engine accepts each number **once only**; it also refuses a number older than a window of 4,096 (`ReplayWindow`, same principle as the IPsec anti-replay window, RFC 4303 §3.4.3). The window allows several requests in parallel to arrive out of order. A recorded request sent again, or a request modified after signing, is refused without an answer |
| Response authentication | Every response (progress messages included) is signed with the key and bound to the sequence number of its request (domain `MAUS-RES`). The interface refuses a response that is not signed for its own request, so an old response cannot be replayed to it either |
| Authorization | The engine runs only operations from the closed list (§1), with the validation of §4. There is no "generic" operation |
| Message bounds | 32 MiB maximum (the length is checked before the body is read; a body within the limit is then read into memory before its signature is checked), one request per connection (after the key presentation, when there is one), a connection has 30 seconds to send its request and does not keep the engine alive meanwhile, JSON into fixed types |
| Lifetime binding | The engine watches the interface process and exits when it exits. If Windows refuses to open that process (interface under another account, see the access control list), the engine stops on the 15-minute idle limit instead. Since 0.8.6 an engine whose interface never presented the key stops after about 60 seconds (`EngineServer.UnclaimedTimeout`; the engine checks every 15 seconds, so the stop comes between 60 and 75 seconds), and when the interface exits, no new request is accepted but an operation already started gets up to 90 seconds to finish (`EngineServer.DrainTimeout`, §9 item 11). A request that the interface gives up (it closes its connection) has its cancellation token cancelled, which stops what can stop; a fix or an undo already started is not interrupted |
| Security stop | After **3** refused connections (another process, a wrong key, a second key presentation on the same connection, a replayed or modified request, a malformed message), the engine stops by itself (`EngineServer.MaxRefusals`, exit code `SecurityStopExitCode`); the interface warns the user and returns to limited mode. The engine takes no action of its own on the PC, but it does not wait for a request in progress: a fix cut off this way stays `Pending` for Undo (§9, items 7 and 11) |

These controls are layered: a request is executed only if it arrives on a local connection, from the process named on this engine's command line, on a pipe that only that account (and, in the case above, the person signed in) can open, signed with the key of this engine start, with a sequence number never used before. Even then, the engine only runs operations from its closed list, recomputed from its own audit and catalogs. Tests: `tests/Maus.Core.Tests/Engine/EngineKeyTests.cs` (signature, fingerprint, replay window), `EngineBrokerTests.cs` (a real pipe: a request before the key presentation, a wrong key, a replayed request and a modified request are all refused; a response is valid only for its own request) and `EngineChannelTests.cs` (a real pipe: the operations of `IMausEngine` with their arguments and results, except `engine.close`, which `OnDemandEngineTests.cs` covers; a set of bounds of §4; the message limits, forged responses refused by the interface, and the stops described above).

## 6. No arbitrary commands, scripts, paths, arguments or executables

- The protocol has no field for a command, script, executable path, registry path, registry value to write or argument list, and every request must be signed with the key of this engine start (§5). The interface sends an operation name from §1, plus identifiers, values from closed sets and the three bounded free texts of §0 (§4). It can also send one folder path, for `space`: the interface only sends the roots of fixed drives, the engine accepts only a local path with a drive letter, whatever its spelling (§4), and the folder is only enumerated, read-only.
- Every executable that the engine starts itself is fixed in code, and since 0.8.6 winget is not one of them:
  - `schtasks.exe`, `pnputil.exe`, `DISM.exe` and `sfc.exe` from `%SystemRoot%\System32` (the non-elevated interface also starts `cmd.exe` and `winget.exe` for the visible consoles of §2.2, `winget.exe` from `%ProgramFiles%\WindowsApps` for the read-only list of §2.4 and §2.5 (what winget then starts: see the limits below), `powercfg.exe` for the battery report and its XML form, and `%windir%\explorer.exe`, only to open a web page, a folder, a file or a Settings page with standard rights; one of those files is a Windows program: the button that opens Windows System Restore asks Explorer to open `%SystemRoot%\System32
strui.exe`, with no argument, and Windows shows its own UAC prompt for that wizard, which is not the MAUS engine; the weekly-audit process, which runs without administrator rights since 0.8.6, starts `explorer.exe` once, to open MAUS again when the user clicks "Open MAUS", §7);
  - the read-only tools of §2.4 from System32 only, never from the `PATH`;
  - bundled PresentMon only after its SHA-256 check;
  - `MAUS.exe` itself for the benchmark, whose only path argument is the output folder that the engine created (§2.3).
- Programs are started with `ArgumentList` (each argument passed separately), with three exceptions that use a single argument string: the `runas` start of the engine (validated pipe name, PID and fingerprint), `explorer.exe` (one quoted URL, folder or file, or a Settings page, or `/select,` followed by one quoted path), and the visible consoles of §2.2, which run without administrator rights. They use a `cmd.exe` command line built by MAUS from constants, from identifiers that passed the validation of §2.2 and from display text. Displayed text is escaped, and the winget path (inside WindowsApps) must not contain a quote.
- Since 0.8.6 every program that MAUS starts, from the engine, from another elevated process or from the interface, has `%SystemRoot%\System32` as its working directory (`SystemTool.WorkingFolder`, the folder given by Windows), never the current folder of the process that starts it; this includes the engine itself when the interface starts it with `runas`.
- No PowerShell, no script host and no `cmd /c` with user text. `ShellExecute` is used only once: to start the engine itself with `runas`.
- Registry writes come only from the plan computed by the engine (§3.1), and since 0.8.6 the accessor refuses any key outside the §3.1 allowlist. There is no "write this value" operation.
- Four of these rules are enforced by an automated test that fails the CI run (`SecurityGuardTests`, §2): where programs are started, `UseShellExecute`, `cmd.exe`, and the System32 working directory of each program started. The others are not covered by that test. GitHub CodeQL (`security-extended`) analyses pushes to `main` and `claude/**` branches, pull requests and a weekly scheduled run.
- **One limit, stated plainly.** MAUS fixes or validates the package id; winget selects the publisher's installer, and MAUS does not inspect it. Since 0.8.6 that installer does not inherit any rights from MAUS: if it needs administrator rights, it asks for them itself, and the user decides on that prompt. The console of §2.2 stays open without administrator rights so that the user can read the result.
- **Process hardening** (`src/Maus.Core/Platform/ProcessHardening.cs`, `SetProcessMitigationPolicy`, applied at start before any request; a window started with "Run as administrator", where the engine stays in the same process, also has `PreferSystem32Images` and RedirectionGuard since 0.8.6, but not the extension-point policy): the interface, the engine and the weekly audit refuse to load DLLs from a remote share or from a file with a low mandatory label (`NoRemoteImages`, `NoLowMandatoryLabelImages`). Since 0.8.6 the programs are also published with .NET startup hooks turned off (`StartupHookSupport=false`, `System.StartupHookProvider.IsSupported` in the runtime configuration), and the published `MAUS.exe` is MAUS's own small native host (`src/Maus.App/Host/MausHost.cpp`, in place of the standard .NET host, with the same file name, process and resources): before loading the runtime, it removes every environment variable that starts with `DOTNET_`, `COMPlus_`, `CORECLR_`, `COREHOST_` or `COR_`. .NET reads these before any managed code, and a program without rights can set them in the user profile, which Windows uses to build the environment of an elevated process. The host then starts .NET in the same process, so the window, the engine after the UAC prompt, the benchmark and the weekly audit are all covered. The elevated engine and the scheduled audit also search Windows DLLs in System32 first (`PreferSystem32Images`), disable legacy extension point DLLs (`ProcessExtensionPointDisablePolicy`), and enable RedirectionGuard (`EnforceRedirectionTrust`): they do not follow a filesystem junction created by a non-administrator account, which blocks the classic trick of redirecting an elevated write. These policies only restrict MAUS's own processes; a policy Windows refuses is logged and skipped, and MAUS does not re-check afterwards that it was applied. Programs started by the engine (`DISM.exe`, `sfc.exe`, `pnputil.exe`, `schtasks.exe`, the read-only tools of §2.4 other than winget, PresentMon) do not inherit them: a mitigation policy is per process. The `cmd.exe` consoles of §2.2 are started by the interface, without administrator rights, and not by the engine. Microsoft notes that such policies are most effective when applied at process initialization: they are applied at the very start of each process, but do not cover what Windows loaded before that point. The benchmark process (`MAUS.exe --benchmark`) applies the engine's policies when it has administrator rights (started by the engine), and the interface's policies otherwise.

## 7. Elevation timing and engine termination per workflow

General behaviour:
- **At start**, there is no UAC prompt. The interface runs as a standard user. At the very first start, and again when the text of the disclaimer changes, the disclaimer and the choice of mode are one single window. On the following starts only the window "How do you want to use MAUS?" appears, until the user ticks "Don't ask me again" or turns it off in Settings > Administrator rights. Both explain the two modes side by side: "Limited mode, without administrator rights" and "All features, with administrator rights". UAC appears **only if** the user clicks "All features"; "Limited mode" keeps MAUS without rights. After an update, "What's new" is a card on the home page (since 0.8.4), not a window. The 0.8.4 home page changes (simple layout, keyboard shortcuts) add no engine operation, no network access, no program start and no file loaded from outside MAUS.
- **Limited mode:** while the engine is not running, every control that needs administrator rights is greyed out (fixes and their restore-point options, undo, repair, driver actions and backups, restore points, weekly audit, protected choices, memory sheet, latency test and its duration, frame counter), and a banner at the top of the window says "Limited mode: greyed-out options need administrator rights" with an **"All features"** button (`src/Maus.App/ViewModels/ElevationState.cs`, `MainWindow.xaml`). No greyed-out control can be clicked. The only action that can bring a UAC prompt for MAUS, other than the controls made for it, is the exception listed under "Switching to all features". Opening Windows System Restore (`rstrui.exe`, through Explorer) can show the UAC prompt of that Windows tool; it gives MAUS no rights.
- **Audit in limited mode (0.8.6):** the audit buttons are never greyed out and never bring a UAC prompt. Without a running engine, `OnDemandMausEngine.RunAuditAsync` sends the audit to the `LocalMausEngine` of the interface process: same read-only modules, standard rights, no write to Windows. Checks that need administrator rights report "not checked". The protected preferences cannot be read, so findings marked "wanted" come back and unticked modules are audited. The screen and the HTML report say that the score is partial, and why. After such an audit the interface does not call `plan`, `journal` or `module`, does not rewrite the "wanted" marks and does not ask the laptop question: each of those would need the engine. It keeps no score, no measure and no audit summary, so nothing from it reaches the curves or the comparisons. It leaves only this in the user profile, for the Follow-up page (§3.2): a line in `health-log.json` with what it could read, marked as read without rights, and the model names in `hardware-card.json`. No fix is prepared from it: applying stays greyed out, and the engine always runs its own audit before any plan or apply. A running engine changes nothing: the audit is then its full audit, as before, except M20, which the interface reads itself without rights (§2.5). If the engine stops between an apply and its check, that check is not done with this audit: the fixes stay "not verified".
- **Switching to all features:** an explicit click on "All features" (banner or startup window) or on "Enable advanced sensors" starts `MAUS.exe --engine` with `runas`; UAC appears at that moment. If two clicks happen together, only one prompt is shown. When the engine is ready, the greyed-out controls become available and the banner disappears. These, and the "Put back in place" button of the weekly-task notice on the home page (§2.3, `schedule.get`), are the only controls made to start the engine: since 0.8.5, the memory sheet no longer does it either (if the engine stopped between the moment its button became available and the click, the sheet says so instead of prompting). There is one narrow exception, traced in the code and not run. It follows a user action, and declining cancels only that action (§8): if the engine stops on idle while a control is still available or its confirmation dialog is open (for example Apply fixes), that action starts the engine again, and UAC appears for it. Two actions never bring a prompt: the language selector is never greyed and re-runs a completed audit, which runs without rights if the engine has stopped; "Save report" reads the protected journal only while the engine is running, and otherwise uses the session it already holds. Copying display choices to the engine, when the protected choices have not changed, never starts it either: the copy goes only to an engine already running (`OnDemandMausEngine.SavePreferencesIfRunningAsync`).
- **Location check before elevation:** before starting the engine, the interface checks that `MAUS.exe` is in a folder that only administrators can modify (`Program Files`, `Program Files (x86)`, `WindowsApps`; `ScheduledAudit.IsInProtectedFolder`). If it is not (for example a copy in Downloads or on a USB stick), another program could have replaced `MAUS.exe`, and Windows would give administrator rights to it. MAUS then warns the user and asks whether to continue (default: No); on No, no UAC prompt is shown and MAUS stays in limited mode. Installed under Program Files through the Microsoft Store, the installer or winget, MAUS is in a protected folder, so this warning does not appear. The check knows only those two Program Files folders: a Store install on another drive (`X:\WindowsApps`) is not recognised as protected, so the warning appears and the weekly audit is refused. This was read in the code, not run with this package.
- **Following actions** reuse the running engine, with no new prompt.
- **15 minutes without any request:** the engine exits (`EngineServer.IdleTimeout`; it checks every 15 seconds), but never while a request is in progress. For example, a running latency measurement or benchmark counts as a request. The interface is notified when the engine process exits (`Process.Exited`): the controls are greyed out again and the banner comes back. If the engine restarted since the last audit, it audits again before any plan or apply, so it never acts on stale data. Automatic refreshes are requests. While the engine runs, the sensor refresh (Live page, monitor window, a running test, diagnosis or recording), the process list refresh (Processes page, diagnosis) and the frame counter refresh reach the engine every few seconds or faster, so the engine does not reach the idle timeout while one of them is active, and it keeps its rights until that view closes and 15 minutes pass, or until the interface exits. If UAC is approved but the engine does not answer the first request, the interface reports an error and stays in limited mode (§3.1 gives the different-account case). It does not stop that engine, which exits with the interface, or about 60 seconds after its start (the engine checks every 15 seconds, so the stop comes between 60 and 75 seconds) if the key was never presented (since 0.8.6), or otherwise after 15 minutes without a request.
- **"Close rights":** while the engine runs, a discreet strip at the top of the interface says so and has a button that stops it (`engine.close`); the interface goes back to limited mode without closing MAUS. A request in progress is never cut short: the button then only says so. Once the engine has accepted, the interface treats it as stopped, even if its process still has a moment to live, and nothing started before the click asks for UAC again: an audit that had already ended finishes as an audit without rights (no plan, no journal, no summary kept), and the cards that read the journal "only if the engine runs" stop there, with no new engine (`OnDemandMausEngine.BrowseJournalIfRunningAsync`).
- **Security stop:** after 3 refused connections (another process, a wrong key, a replayed or modified request; §5), the engine stops by itself with a dedicated exit code; the interface goes back to limited mode and warns the user that a program tried to control the engine, and advises a scan with Windows Security. Nothing else is done (no action on the PC that a malicious program could abuse). An operation in progress is cut, not finished (§9, item 11).
- **Interface closed or crashed:** the engine detects that the interface process has exited, accepts no new request, gives an operation already started up to 90 seconds to finish (since 0.8.6), and stops. If a fix is still being written after that limit, the journal keeps it as `Pending` and "Undo" handles it (§9). Closing MAUS during an apply, an undo or the creation of a restore point asks for confirmation first (§9, item 11).
- **MAUS started with "Run as administrator" by the user:** there is no separate engine; the same operations run in-process (`LocalMausEngine`). In that mode there is no second confirmation by the engine (§8), because there is no second process: the interface dialogs are the only confirmation, and everything the interface does runs with the rights the user gave it, except the battery report, the winget consoles and the winget list, which such a window refuses (M20 then reports "not checked" and says why), and the benchmark result, which it does not write in the user profile (§2.2 to §2.5).
- **Weekly audit (only if the user enabled it):** since 0.8.6 the task `\MAUS\WeeklyAudit` (§2.3) starts `MAUS.exe --scheduled-audit` **without administrator rights**: a task created by 0.8.6 never elevates without a UAC prompt. A task left by an earlier version can still start elevated once: that process then re-creates the task without rights, with no question because this only removes rights, after the `IsMausTask` check, and exits without auditing (`TaskSchedulerClient.DropRightsOfOldTaskAsync`). Checks that need administrator rights report "not checked" in that audit, and it records no score, because a partial score would look better than reality. It does record a summary of its findings without a score, marked as weekly and never compared with audits started by the user; if a module failed, it records no summary at all. That process applies the process hardening of §6, changes no system setting and applies no fix, uses no network, writes in the user profile only that summary (`audit-snapshots.json`), a line of the health log with what it could read (`health-log.json`), the note of an alert that was not answered (`settings\alerte-sans-reponse.txt`: a date and a number of problems, written before the notification is shown and removed when the user answers; the interface reads and deletes it at the next opening, and no decision depends on it), its crash log and, when the user clicks "Open MAUS" or the notification title, the display choice that opens MAUS on its home page, and exits unless there is something to show: by default a red problem; the user can choose a summary after every audit or no notification at all (`WeeklyNotification`; it reads the copy of the choices kept in its own settings file). In that case it shows a notification; "Open MAUS" or its title starts MAUS again as a normal process, which shows that summary on its home page. To fix something, the user chooses "All features" and the usual UAC prompt appears.

## 8. Confirmation before changes, and declined UAC

**First start:** the user must accept a disclaimer (what MAUS does, the risks, and that the user decides); otherwise MAUS closes.

**Before every modifying action**, except those listed in this paragraph, the interface shows a Yes/No dialog whose default button is **No**. It describes what will change and, where an undo exists, how to undo it. Actions with no dialog: removing a "wanted" mark and setting other MAUS preferences, such as the laptop power choice or the Game Bar profile, except profiles 1 and 2 on a Ryzen X3D (they only change a MAUS preference); disabling the weekly audit (it only removes MAUS's own task); and starting the benchmark, the latency test or the frame counter (they change no setting). One dialog has **Yes** as its default: if another MAUS is running with no window, a new launch asks whether to close that stuck copy, because it can block the memory bus (`App.TakeOverFromWindowlessInstance`). On Yes, `SingleInstance.CloseWindowlessOthers` calls `Process.Kill` on the other `MAUS.exe` processes that have no window, with the rights of the new launch. This is not an engine operation. The Yes/No dialog is the user's consent step; it lives in the non-elevated process, so it is not a barrier against code already running in the user's session: that barrier is the engine's own confirmation below, which covers the most sensitive operations.
- **Apply fixes:**
  - the dialog shows the list of chosen changes, their warnings, whether a restore point will be created, and a reminder that the user decides;
  - fixes are chosen one by one in a checklist: "recommended" ones are pre-checked, "advanced" ones never are, and "warning" ones show a reinforced warning;
  - the restore-point checkbox is pre-checked.
- **Undo** a session or one fix. For a setting that starts a program or carries a security policy (listed below), the dialog also shows the value that would come back. "Undo today" and "Undo everything" leave those values out and say so: they are undone one by one, from the History page.
- **Repair Windows files** (DISM/SFC).
- **Restart Explorer.**
- **Create a restore point.**
- **Enable the weekly audit,** or put it back in place from the notice on the home page (§2.3). Disabling it removes only MAUS's own task, without an extra dialog.
- **Terminate a process:** the dialog warns that unsaved work is lost.
- **Install or remove PawnIO.**
- **Each driver action** (restart, remove and re-detect, back up, back up then delete) and each driver restore. Before a delete, a verified restore point is created first; if it fails, the user is asked whether to continue.
- **Software upgrades:** an explicit checklist of packages, then a console where winget itself asks the user to accept licence terms.
- **Refresh-rate trial:** confirmation first, then a "Keep?" window that rolls back automatically after 15 seconds.
- Marking a finding as "wanted" and choosing Game Bar profile 1 or 2 on a Ryzen X3D also ask for confirmation.

**Second confirmation shown by the elevated engine itself** (since 0.8.4, `src/Maus.Core/Engine/Broker/EngineConfirmation.cs`): the interface runs without administrator rights, so a malicious program running under the same account could in theory inject into it and send signed requests while the engine is running. For the most sensitive operations, the engine therefore asks again in a window of its own, before doing anything. Since 0.8.6 this is a small WPF window of the engine process (`src/Maus.App/Views/EngineConfirmationWindow.cs`, shown on the engine's application thread by `EngineConfirmationPrompt`), in place of the earlier Windows message box. It is topmost, activated when shown and centred on the screen, with the title "MAUS (administrateur) : …" and a question written by the engine (never text from the channel). Its two buttons stay disabled for 2 seconds after it is shown, and again for 2 seconds each time it comes back to the foreground, with a visible countdown; they are disabled while it is in the background. No button has an access key, none is the default button, and the initial focus is on **No**. Esc, the close button and Alt+F4 answer No, and so does no answer after 2 minutes. Yes is given by a mouse click, or from the keyboard (Tab to Yes, then Space or Enter) only when no key has been pressed for 2 seconds, so that typing meant for another window cannot answer it. If the engine process has no WPF application, or the window cannot be shown, the answer is No. The timing rules are in `EngineConfirmationGate` (`src/Maus.Core/Engine/Broker/EngineConfirmation.cs`) and have automated tests. The questions cover:
- terminating a process (`process.terminate`);
- every graphics-driver action: restart, remove and re-detect, back up, back up then delete, and reinstalling a driver backup (`tool`, driver tasks; restart and back up since 0.8.5);
- marking a finding as "wanted" (`prefs.save`, when it is added to the list, and since 0.8.6 when the recorded value of a mark changes; rewriting a mark after a language change does not ask, provided the finding is in the engine's own audit, the mark carries the language of that audit and its text is the one the engine read, in the bounded form of §4; anything else asks, including when the engine has not audited yet);
- choosing to be told nothing after the weekly audit (`prefs.save`, only when the choice becomes "never"; 0.8.6). This question covers the protected file. The weekly audit runs without rights and reads its copy of the choices, including the "wanted" marks, in the user's settings (§7): that copy decides only what its notification shows, it is not protected from a program under the same account, and the engine never reads it;
- unticking an audit module (`prefs.save`, only when a module is added to the list; 0.8.6);
- undoing a fix when that would put a value back in a setting that starts a program or carries a security policy (`revert`; `SensitiveSettings`): Winlogon `Shell` and `Userinit`, `AppInit_DLLs` and `LoadAppInit_DLLs`, IFEO `Debugger`, the UAC values, the Defender and firewall policies, SmartScreen, the start type of the Defender and firewall services, the Windows Update server and automatic-update policies (`WUServer`, `WUStatusServer`, `DoNotConnectToWindowsUpdateInternetLocations`, `UseWUServer`, `NoAutoUpdate`), the start type of the update services (`wuauserv`, `UsoSvc`, `WaaSMedicSvc`, `BITS`, `CryptSvc`, `TrustedInstaller`), and the M13 kernel protections (`VulnerableDriverBlocklistEnable`, `FeatureSettingsOverride`, `FeatureSettingsOverrideMask`). A group undo leaves these values out and says so; each is undone one by one. The window shows each setting and the exact value read from the protected journal. It is asked only when a value would really be written; removing a value that MAUS added does not ask. On "No", nothing is restored;
- a fix that disables a program of the catalog's `security` family at startup, whether a startup entry or a logon task (`apply`). The engine writes the question from its own plan, never from text received from the interface. On "No", no fix of that request is applied.

An ordinary fix, and undoing it, ask nothing more here, so that this window stays rare and is read.

The other modifying operations of the engine (other fixes and undos, restore points, creating the weekly-audit task, Windows repair) rely on the interface dialog and on the closed list; software upgrades and PawnIO are no longer engine operations (§2.2): they rely on the interface dialog and start without administrator rights; removing the weekly task, the latency test, the frame counter and the benchmark have no dialog and rely on the closed list alone. All of them can only do what the engine's own plan, lists and catalogs allow. A program without administrator rights cannot click or type in a window of the elevated engine: Windows User Interface Privilege Isolation (UIPI, Microsoft "Windows Integrity Mechanism Design") blocks it. A "No" returns a message to the interface and nothing is done. A "Yes" no longer acts if the interface has abandoned the request in the meantime. The interface calls `AllowSetForegroundWindow` for the engine process before each request so that this window can come to the front. When MAUS itself was started with "Run as administrator", there is no separate engine and only the interface dialog is shown.

Admin actions that only **read** (sensors through PawnIO, memory sheet, latency, frame counter, journal) have no MAUS dialog: they run only after the user accepted a UAC prompt (§7, including its exception); that is the consent. The audit has no MAUS dialog either: it runs with administrator rights only in an engine the user already accepted, and otherwise without rights.

**UAC declined:** Windows returns error 1223 (`ERROR_CANCELLED`). MAUS throws `EngineDeclinedException` and shows: "Autorisation administrateur refusée : rien n'a été lancé. MAUS reste en mode limité, sans droits administrateur." (Administrator permission refused: nothing was started. MAUS stays in limited mode, without administrator rights.)
- Nothing is started and nothing is written.
- MAUS stays in limited mode: the controls that need administrator rights stay greyed out, and the "All features" button can be clicked again later.
- There is no retry loop, and no fallback that performs the action without elevation.

## 9. Restore point, partial failure, cancellation, logging and undo

Implemented in `src/Maus.Core/Fixes/FixEngine.cs`, `RestorePoints.cs`, `JournalStore.cs` and `AtomicFile.cs`. Items 1 to 10 describe fixes applied through `FixEngine`; item 12 says what they do not cover.

1. **Blocked cases.** No fix is written in these cases (a restore point, when requested, is created before the journal folder is checked, so it can exist when the apply then stops):
   - the PC is managed (domain or MDM enrolment), or that cannot be read: an unreadable domain state or MDM enrolment, with no proof of management elsewhere, blocks fixes the same way and only reading continues;
   - the engine is not elevated;
   - the journal folder cannot be secured (`JournalUnsafeException`).
2. **Restore point first.** When the restore-point option is on (pre-checked), a restore point is created before any write and then **verified** by re-reading the list of restore points.
   - If system protection is off, it is enabled only if the user ticked that option; otherwise the point fails.
   - If the point fails, the apply stops with "Aucune correction n'a été appliquée." (no fix was applied). The user is then asked whether to continue without a restore point (explicit `ProceedWithoutRestorePoint`; default: no). No fix has been written at that point. If system protection was enabled just before (the ticked option), it stays enabled: MAUS does not turn it off (item 12), and the user can do so in Windows settings.
   - If the user unchecks the option, the confirmation dialog says so beforehand, and the journal records "restore point not requested by the user".
3. **Journal before write.** For each value of a fix, the original value is read just before writing, together with whether its key existed (a key created by an earlier fix of the same session counts as not existing, so the last undo removes it when empty; only that last key is removed, parent keys created along the way stay). It is saved to the protected journal (state `Pending`) **before** anything is written.
   - If the original value cannot be read, that fix is skipped and nothing is written.
   - A value already changed by another fix of the same session is skipped.
   - A value already at the target is not written.
4. **Write, then read back.** Each write is read back. If any write of a fix fails, or reads back differently, **the whole fix is rolled back** in reverse order (all-or-nothing per fix), and each restored value is re-read. The result names the failed fix and the reason. The other fixes chosen in the same session are reported separately.
5. **Rollback failure.** If a rollback itself fails, the entry is marked `RollbackFailed` and shown to the user, and "Undo" stays available to retry.
6. **Journal failure during a session.** If the journal can no longer be written, whatever the error (not secured, disk full, file locked, access denied), no further write is made and the writes already made in the session are rolled back. The result says the apply stopped, and no fix is reported as applied (since 0.8.6). A rollback that fails is handled as in item 5.
7. **Interruption.** If the engine makes a security stop (§5), a crash occurs during a write, or MAUS is closed and the write outlasts the 90-second wait (item 11), the next "Undo" handles the `Pending` entries:
   - if the original value is still in place, nothing had been written;
   - if the new value is in place, it is restored like an applied fix.
   - Exception, traced in the code and not run: if the engine stops while a restore point is being created (a security stop, a crash, or MAUS closed and the creation outlasting the 90-second wait), `SystemRestorePointCreationFrequency` can stay at 0, and the effect is that Windows no longer skips a restore point made within 24 hours of another. It is not journaled, so Undo does not restore it. Since 0.8.6 its original value is kept in `restore-frequency.memo` (§3.2) while it is at 0: the next restore point made by MAUS puts that value back afterwards, unless something else changed the value in between; until then it stays at 0. If only the write that puts the value back is refused, the point is still reported as created and verified, and the message says the value stayed at 0.
8. **Effect check.** After the apply, the interface runs a fresh audit and tells the user which fixes were written but have no visible effect (for example a policy ignored on the Home edition). This note is stored in the journal (`verify`). If that audit fails, the fixes are shown as "not verified", never as "no effect".
9. **Undo.** Undo works by session or by single change (History page; `--revert` in the separate command-line tool, which is not part of the Store package), and each restored value is re-read. The journal is common to the whole PC, so since 0.8.6 each session records the SID of its account. A value in the profile of another account (HKCU, `SystemParametersInfo`) is never restored from the wrong account, even with `force`: it is reported as such and stays outstanding for its account. Settings common to the PC can still be restored by another administrator, but only for that one session, after the interface has said it belongs to another account; "undo all of today" leaves such sessions out. It also leaves out any fix that would put a value back in a setting that starts a program or carries a security policy: those are undone one by one, with the value shown by the interface and confirmed in the engine's own window (§8). A session written before 0.8.6 has no account recorded and is undone as before. If a value was changed by something else since MAUS wrote it, MAUS **leaves it as it is** and reports "changed since". Neither the interface nor the engine's channel can overwrite such a value (the engine ignores `force` from the channel, §4); only the separate command-line tool, not part of the Store package and started by an administrator, offers `--force`. A value already back at its original state needs no write: it is reported as "already in place" and the entry no longer counts as outstanding. The journal is saved after each restored value; if that save fails, no further value is restored, the values already restored stay restored, Windows is told about them, and the result carries the error next to the per-value list. A setting of another profile (engine started with another administrator account) is not written and stays to undo from the user's own session.
10. **Logging.** The journal is one JSON file per session in `%ProgramData%\MAUS\journal` (SYSTEM + Administrators), written atomically. A session file whose owner is not SYSTEM or Administrators, or that is a link, is ignored and never replayed. Crash logs of the interface and of the weekly audit, which runs without administrator rights, are written to `%LOCALAPPDATA%\MAUS\logs`; those of the engine, the elevated benchmark, a window started as administrator, and a weekly audit still started elevated by the task of an earlier version go to `%ProgramData%\MAUS\logs` (SYSTEM + Administrators) since 0.8.6; when that folder cannot be protected, they are not written to disk at all (§3.2). If a protected folder of `%ProgramData%\MAUS` was pre-created by another account, the engine moves it aside under a random name, never reads it, and creates a new folder with the protection, so a handle kept by that account has no effect (0.8.6); if it cannot be moved, no change is made, as before. A folder owned by SYSTEM or Administrators with wrong permissions has them re-applied, if necessary with `SeTakeOwnershipPrivilege` and `SeRestorePrivilege`, enabled only for that operation (`src/Maus.Core/Platform/TokenPrivileges.cs`, 0.8.6). Nothing is sent anywhere. There is no persistent log of engine requests. Only fixes applied through `FixEngine` are recorded, in the journal. The engine's diagnostic breadcrumbs, including refused connections and operations that ended in error, are an in-memory list of the last 60 lines, written to disk only in a crash log. They are lost when the engine stops normally or by the security stop; in that last case the user's warning (§7) is the only record.
11. **Cancellation.** Before writing, "No" in the confirmation (§8) or in the "continue without a restore point" question (item 2) ends the action with no fix written. Once writing has started there is no Cancel button: `FixEngine.Apply` takes no cancellation token and runs to the end. Closing MAUS during an apply, an undo or the creation of a restore point asks first (default No); on Yes the interface closes and, since 0.8.6, the engine accepts no new request but lets the operation already started finish, for up to 90 seconds, before it stops (`EngineServer.DrainTimeout`). A fix cut off after that limit stays `Pending` for "Undo" (item 7). MAUS has no cancel control for a console: the user closes its window. The benchmark stops with Esc. A latency measurement has no cancel control in the interface: it ends at its chosen duration or when the engine stops. Undo has no cancel control either: `FixEngine.Revert` takes no cancellation token. It saves the journal after each restored value, so if the engine stops during an undo, at most the value being restored at that moment still shows as applied; a later Undo finds its original value and reports it as already in place. A security stop (§5) does not wait: it cuts a running apply, undo or restore point at once, without asking, and item 7 then applies. The audit, the memory reading and restore-point creation have no cancel control. A memory bus read cannot be interrupted: the interface stops waiting, and the engine refuses another read and does not reach its idle timeout until the first ends. The "Stop" button of the disk-space analysis stops the enumeration in both modes: when the engine runs the analysis, the connection closes and, since 0.8.6, the engine sees it and cancels the read-only enumeration. If the engine process is killed, no MAUS code runs at that moment to stop the `NT Kernel Logger` session or PresentMon. Since 0.8.6, an unhandled error and `Environment.Exit` during a measurement close the session at process exit, closing the engine cancels the measurement and waits up to 5 seconds, and the session of a killed engine is closed at the next engine start or measurement (§2.3); until then it stays open, as it does if the conditions of §2.3 are not met, and the measurement error then says to close the other tool or restart the PC. The decision logic and the cancellation have automated tests; the ETW calls themselves need administrator rights and a real session, and all of this was traced in the code, not run.
12. **What this section does not cover.** Tool operations (DISM/SFC, driver actions), winget upgrades, PawnIO and process termination create no journal entry and have no MAUS "Undo"; their record is the MAUS tool window, the visible console or an on-screen message. The same is true of creating a restore point, enabling system protection (§3.3), the weekly task (§2.3) and the refresh-rate setting (§3.3). A driver delete is preceded by a backup, which is required, and by a request for a verified restore point; if the point fails, the user decides whether to continue (§3.3). PawnIO is removed through winget (§2.2); the weekly task is removed by turning it off. A failed manual restore point (`restorepoint.create`) only returns an on-screen message: nothing else is changed, and the frequency value is restored as in §2.3. Partial failure: `sfc` runs even if `DISM` fails, `/scan-devices` runs even if `/remove-device` fails, and each winget upgrade runs even if an earlier one failed; Backup and Remove stop when the export fails. For tool operations, the engine returns a result text based on the exit codes (§2.2). For winget, the interface reports only that the window opened; the result is what the console shows.

## 10. Separation of read-only audit and privileged modification

| Layer | Rights | What it can do |
|---|---|---|
| Audit modules (`IAuditModule.DetectAsync`, `IFixableModule.Plan`) | Read-only by contract | They receive `AuditContext`: registry **reader**, WMI/CIM reader, event-log reader, package and file readers, and `ReadOnlyCommandRunner` (§2.4). It contains no writer. Some modules also make the direct read calls listed in §2.5. These are ordinary code in the same process: separation from writers is by design and review, not a technical barrier. Unit tests run every module with fakes, and an apply/undo round-trip test checks each fixable module |
| `FixEngine` (`Apply`, `RecordVerification`, `Revert`) | The only writer of fix settings | It receives `FixContext` (writers + journal), which is separate from `AuditContext`, and writes only `PlannedChange` objects produced by the engine's own `Plan`. Changes outside fixes, all listed in §3: `RestorePointCreator` sets the restore-point frequency value to 0 around the call, then restores it, and can enable system protection during `apply`; `schtasks` for the weekly task; the Windows tools of §2.2 (DISM, SFC, pnputil); and, in the interface, the refresh-rate mode |
| Engine Workshop operations (§2.2, §2.3) | Engine | Fixed executables and validated inputs; a confirmation in the interface, except for the actions listed in §8 that have none |
| Interface | Standard user | Displays results and sends operation names and ids. It never accesses the protected journal, the protected preferences or the privileged tools directly; everything that needs the engine goes through `EngineHost.Current`. It does act on its own, without the engine and without rights, for the Explorer restart, the refresh-rate trial (§3.3), the CPU/RAM/VRAM stability tests, the disk speed test (§3.2), the ping test, the battery report and its XML form, the winget list (§2.5), the reads of §2.6 that it makes itself, reports saved where the user chooses, and its own files in the user profile (display settings, score history, benchmark history, including the result and image of a run started by the engine (§2.3) and the path of the benchmark result image that it decodes and can open) |

The audit modules do read, in the elevated process, inputs that a standard user can influence: the `Run` values of HKCU (M01 checks the signature of the program they point to with `WinVerifyTrust`), the shortcuts of the Startup folders (M12 parses them with MAUS's own bounded parser; a file above a fixed size is skipped), and the outputs of the read-only commands of §2.4. These inputs are parsed into typed values; a parser failure turns the module grey (no result) and never into an action.

Since 0.8.6 the read-only audit does not depend on the elevated engine at all: without it, the audit runs with standard rights in the interface and no UAC prompt appears (§7). Everything that modifies the system stays in the engine. The audit can be run as many times as the user wants without changing any setting. No fix is ever applied automatically, including by the weekly scheduled audit, which changes no system setting and applies no fix: it notifies, and writes only its audit summary, one line of the health log, the note of an unanswered alert, its crash log and, on "Open MAUS", one display choice in the user profile (§3.2, §7). One read operation of §1 does make one small change: `drivers.backups` re-applies the protection of MAUS's backup folder (§2.5). A result image of the benchmark is read by the interface only from MAUS's own images folder in the user profile, whatever path the history file holds (0.8.6). Reading through PawnIO also involves the hardware writes stated in §3.3, within the limits stated there; `latency` and `frames.start` open temporary ETW sessions.
